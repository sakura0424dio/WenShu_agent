# 05 · 复盘：最难问题、学习收获与下一步

## 1. 最难的问题

### 1.1 “工具成功”不等于“方案成功”

最容易写出的错误实现是：只要四个工具都返回 200，就把任务标成功。但预算 5 时，估算工具会成功返回 P-VIDEO 15.00；方案依然不可行。项目把“工具执行状态”和“业务可行性”分开：

- Step/Task 记录工具真实返回；
- 最终是否 `completed` 由 `finalize` 检查预算、时间、保存和活动任务共同决定；
- 无可行方案时保留全部成功估算，但终态是 `incomplete`，并给出最低可行成本与差额。

这个问题决定了整个状态模型：工具事实、业务任务、运行终态必须是三层，而不是一个 `success` 布尔值。

### 1.2 动态决策不能依赖“假分支”

需求明确排除“固定条件分支 + 自动重试 + 预设决策日志”的伪 ReAct。实现上：

- 模型每轮只输出一个动作，执行结果作为观察回溯；
- `guard` 可以拒绝非法动作并回溯观察；
- 换方案、失败重试、部分成功继续、主动停止都由观察驱动；
- Mock 虽是规则策略，但读取真实状态与工具结果，且 Trace 保留决策依据；
- 真实模式把同一状态交给 DeepSeek，不预设工具顺序。

难点不在“写出循环”，而在让循环真的根据工具结果改变下一步，同时又不让模型绕过状态约束。

### 1.3 失败步骤必须记录

工具失败后，常见错误是重试成功后把旧失败删除或改成功。本项目保留所有 Step，重试产生新 Step ID；换方案时旧任务标 `superseded`，原状态不变。

A-08 续跑时，父运行的失败 Step 也保留在子运行历史中，同时用 `inherited_from_parent` 标明来源、用 `from_parent_run` 标明哪些成功结果被复用。失败步骤不计入 `reused_steps`。

### 1.4 续跑的语义边界

“从检查点恢复”听起来简单，但业务上容易混淆：

- LangGraph 检查点保存的是 superstep 状态，适合审计；
- 业务续跑需要明确“复用哪些成功结果、失败步骤怎么办、是否允许改预算、是否清空注入”；
- 因此选择应用层状态快照 + 新线程：复制成功结果，失败保留，重置计数和注入，新 Step ID 继续。

这样做的代价是不能跨进程从任意中间点恢复；收益是语义可解释、可测试。

### 1.5 幂等与内容寻址

重复执行有两个层面：

- 同一 `Idempotency-Key`：直接返回原报告；
- 无幂等键但相同输入：仍创建新运行，保存工具用内容哈希返回同一 `plan_id`。

内容哈希最初包含 `run_id`、`estimate_id`、`available_minutes`，导致重复运行生成不同方案，违反“同一输入行为明确”。修正为只覆盖稳定方案语义，排除了运行字段。

### 1.6 Trace 的“后续动作”与归属

Trace 不仅要记录“做了什么”，还要能回答“看到结果后下一步做了什么”。最初 `tool_result` 只有返回摘要，后续动作靠下一条事件推断；后来增加 `decision_id` 与显式 `next_action`，使每条记录可直接核对。

续跑时还遇到一个更隐蔽的问题：父运行步骤的 `decision_id` 与子运行决策编号重复，导致历史步骤被错误地挂到子运行的 `tool_result` 下。修复方式是给所有复制步骤加 `inherited_from_parent`，Trace 只把本次真正执行的步骤归入 `tool_result`，历史步骤统一走 `inherited_step`。

## 2. 学习收获

1. **状态记录比提示词更能保证真实性**。把“谁能写状态”写进节点职责，比在提示词里反复要求“不要撒谎”可靠。
2. **观察要结构化**。错误码、是否可重试、部分结果 warning、费用明细，必须进入模型上下文和 Trace，否则“动态调整”无从谈起。
3. **上限和停止是产品语义**。达到上限不是异常 500，而是业务终态；报告要说清已保留什么、还差什么。
4. **可复现性需要设计**。固定时钟、合成数据、确定性 Mock、Decimal，让示例和测试可以逐项复算。
5. **加分项往往是状态一致性问题**。续跑、幂等、内容去重不是“多写一个接口”，而是要对步骤、任务、费用、保存结果做统一约束。
6. **Trace 是证据，不是日志**。事件字段要能直接支撑验收：参数、摘要、后续动作、决策依据、继承来源缺一不可。
7. **AI 生成代码必须验证**。设计文档再完整，也可能与实现漂移；本次通过 compile、pytest、真实 HTTP 示例和逐字段检查发现了多个问题（循环、重复 caveat、绝对路径、无解分支、续跑 Trace 归属等）。

## 3. 下一步

按优先级：

1. **真实模型固定评测集**：已完成 `deepseek-flash` 的 9 组冒烟（正常、超预算、工具失败、无解、部分成功、续跑、幂等、上限），下一步应固定输入集比较不同模型/提示词的成功率、重规划合理性与费用误差，而不是只做单次冒烟。
2. **工具级缓存**：按工具名 + 参数 + 数据/价格版本缓存 `success`，续跑与重复执行减少实际调用；注意不缓存 `failed`，`partial` 默认重试。
3. **持久化拆表**：把 `steps`、`tasks`、`plans` 从 `state_json` 拆成独立表，支持跨进程查询与大运行。
4. **并发与队列**：当前同步单进程；生产化需要任务队列、幂等键分布式锁、运行状态推送。
5. **更强的依赖校验**：把任务依赖图从隐式规则升级为显式 DAG，支持并行子任务与阻塞传播。
6. **可观测性**：结构化日志、指标（tool latency、replan count、incomplete rate）、Trace 轮转与脱敏。
7. **真实模型 Trace 统一格式**：后续版本可在真实模型运行中也生成显式 `next_action`，让 Mock 与真实记录使用完全一致的字段；当前历史记录保持原样。
